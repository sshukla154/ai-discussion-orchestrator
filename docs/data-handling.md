# Data handling

The project has a hard rule that no credential is ever published. That rule is satisfied by
construction: the challenger is manual, so **no API key, token or secret exists anywhere in this
project**. There is nothing to leak.

Content is the harder problem, and it deserves a written decision rather than an assumption.

## What actually leaves the machine

Two egress paths, and only two:

1. **To Claude**, via the CLI, using an existing authenticated session. Covered by whatever
   agreement already governs that account.
2. **To ChatGPT**, by a person copying a generated prompt into the web interface and pasting the
   reply back.

The second path is the one that needs a rule. The prompt is generated by this application and
will contain whatever the discussion is about — which, for architecture questions, may be real
system design.

## The rule

**Treat a challenger prompt as if you were posting it publicly, because you are handing it to a
third party under consumer terms.** Concretely:

- The ChatGPT Free tier uses conversations to improve the model by default. It can be turned off
  in that product under the setting that controls whether your content improves the model for
  everyone. Decide once, deliberately, rather than discovering it later.
- Do not paste anything you would not put in a public design document: customer names, internal
  hostnames, credentials of any kind, personal data, or anything under a confidentiality
  obligation that is not yours to waive.
- Generalise before asking. A challenge is usually *better* when the question is abstracted —
  "a single-writer embedded database with a five-minute external call" is both safer and a
  sharper question than a verbatim internal design.
- The application never sends anything automatically. A person reads every challenger prompt
  before it goes anywhere, which is the actual control here, and is worth preserving even when it
  is inconvenient.

## What is stored locally, and why it matters

The database holds complete transcripts of every discussion. That makes it the most sensitive
artefact in the project — more so than any configuration file.

- It lives outside the repository, under a local application-data path. Not in the working tree,
  and not on a synchronised or network drive: the write-ahead log requires real shared memory and
  breaks on network filesystems, quite apart from the exposure of syncing transcripts to cloud
  storage.
- `*.db`, `*.db-wal`, `*.db-shm`, `runs/` and `.env` are all ignored, and CI fails if any of them
  ever becomes tracked. Belt and braces, because the consequence of a mistake here is a public
  repository full of private reasoning.
- Prompts and responses are never logged at INFO. They appear at DEBUG only, to a local file, and
  the same handling rules apply to that file — a debug log is exactly the artefact that ends up
  pasted into a public issue tracker.

## Untrusted content

One model output becomes another model input. Anything arriving from a provider, including a
reply pasted in by hand, is **data to be argued with, not instructions to be followed**:

- The CLI is always spawned with tools disabled and no project configuration, so a prompt
  injection has no filesystem or command surface to reach for.
- Foreign content is wrapped in a delimited, labelled block that says what it is.
- Control decisions — whether the discussion has converged, whether to stop, what was decided —
  are read **only** from schema-validated typed fields, never parsed out of prose. A model cannot
  end a discussion by writing a sentence that looks like a verdict.
